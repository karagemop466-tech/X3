Strategies, gates and the leaderboard that stays empty

The brief asks for a leaderboard competition with rewards for top strategies, each strategy passing validation gates, correlations computed, and luck removed. This page states what can be built today, what cannot, and the rule that decides which is which.

The rule that governs every row below

A strategy enters the leaderboard only when it has (1) a registration frozen in git before results were seen, (2) a proper score against a naive benchmark with an interval, and (3) prices for the bets it would have made. At 2026-11-18T03:20Z no strategy clears (3), because the repository holds zero market prices. Therefore the leaderboard is empty by rule, not by oversight — an empty board is the correct output, and a filled one would be a fabrication.

2. Signal and staking, kept apart

The brief's requirement is that a lucky staking run must not mask a bad signal. The repository's own scoring contract already says the right thing: signal and staking are scored in separate columns from different data and are never combined into one number; a good staking run cannot promote a strategy whose signal is inconclusive, and a good signal cannot be published with a staking number that does not exist. But it also says a strategy is leaderboard-eligible only when both exist — and staking cannot exist without prices. So the honest state is:

3. The gates a strategy must pass, in order

  1. Registration. The rule text, the sample window and the gates are committed before the evaluation window opens. The commit hash is the registration. Result-chasing is not a risk to be managed later; it is prevented here or not at all.
  2. Data provenance. Every input traces to an official page, or to a documented dataset with a link and a clock time.
  3. Out-of-sample scoring. Train, validation and a final holdout that is never touched during development. The repository holds one season, so the holdout does not yet exist.
  4. Proper score with uncertainty. Brier or log score against a naive benchmark, with a game-cluster interval, never a win rate.
  5. Multiplicity. The number of strategies tried is recorded and the interval adjusted for it, otherwise the best of fifty coin flips looks skilled.
  6. Price and staking. Only then, and only against an admitted price.

4. Correlations

Every correlation the brief asks for — same-game leg dependence, prop-to-result dependence — needs paired outcomes from the same games. The repository holds no game-level scoring table, so zero correlation values are computed. The register stores the pair, the method and a blank value with an UNVERIFIED marker, which is the only defensible state. Publishing an n without the paired data behind it would be the fabrication this board exists to avoid.

5. Rewards

The brief asks for rewards for top strategies. No reward can be computed honestly until returns can be, and returns need prices. Beyond that, a reward paid on realised return is a reward for luck, as the luck panel shows directly. A defensible design pays on out-of-sample proper-score skill with a multiplicity penalty, and does not pay on ROI. That is a proposal on Suggestions, not an implemented rule.
