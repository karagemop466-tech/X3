The eight requirements as acceptance tests

Read each test, then read what the repository does. The gap between them is the work. Every verdict is linked to the file it was measured in.

Each requirement of the brief is restated as a test the repository either passes or fails. A requirement is MET only when its acceptance test passes on published data; PARTIAL when part of it passes; NOT MET when nothing satisfies it; BLOCKED when it cannot be satisfied without a decision or a purchase. Verdicts come from reading the files, not from intent.

R1 Price-snapshot store that records opening and closing numbers for every market we originate BLOCKED

Without both ends of the price, closing-line value cannot be measured, and without closing-line value a hit rate is not evidence of skill.

Acceptance test. For every originated market there is one row per book carrying market_id, book, open_price, open_timestamp, close_price, close_timestamp, price_format and source_url. A market cannot be graded unless open and close are both present.

Status. Store specified, zero rows. No price feed exists in the repository.

Owner. origin/data/snapshots.json (claimed by session arena/f2df8317-x3, in progress)

Blocker. A data-rights decision, not code. See suggestion S01.

Evidence. UNVERIFIED - no price feed

R2 Verified results feed so backtests and ROI can be computed at all PARTIAL

ROI is (settled return - stake) / stake. Every term needs a settled result, so without a results feed no leaderboard row can be scored.

Acceptance test. One row per completed game with final score for both clubs, the official source URL, the retrieval timestamp, and a written settlement rule per market type (side, total, moneyline) including how ties and pushes are treated.

Status. Game results are in place and verified; settlement rules and prop results are not.

Owner. data/desk/games.json (session arena/3bf7cc8b-x3) + origin/data/results.json (claimed)

Blocker. No settlement rule is written down, and no player-prop results exist. See S02, S09.

Evidence. nfl.com week schedule pages (captured 11/11 HTTP 200)

R3 Originate the side first, then the total, then the moneyline NOT MET

The moneyline is a function of the expected margin and its uncertainty. Deriving it last keeps the three markets mutually consistent; deriving them independently produces arbitrage against yourself.

Acceptance test. Each game carries three originated rows in the order side, total, moneyline. The moneyline row records the margin and the sigma it was derived from, so it is reproducible.

Status. Side and total exist for 13 games. No moneyline is originated anywhere in the repository.

Owner. data/desk/model.json (side + total) ; moneyline claimed by origin/ (session arena/f2df8317-x3)

Blocker. Third market type not built yet. See S03.

Evidence. repo artifact - side and total, DERIVED

R4 Publish the model's fair line, the market line, and the difference as separate columns BLOCKED

The difference is the whole signal. Publishing only a fair line leaves the reader to do the subtraction against a price they cannot see.

Acceptance test. Three distinct columns per market: fair_line, market_line, and edge = fair_line - market_line, each with its own units label and sign convention.

Status. Fair line published and badged DERIVED. Market line is an empty string in all 13 rows, so the difference cannot be computed.

Owner. data/desk/model.json

Blocker. Depends on R1. No official source publishes NFL prices. See S01.

Evidence. repo artifact - market columns empty

R5 Separate 'signal' from 'staking' in the leaderboard so a lucky staking run cannot mask a bad signal NOT MET

A flat-stake record measures whether the fair line was right. A sized record mixes that with how much was risked. Ranking on the blend lets a Kelly run on coin-flips outrank a real edge.

Acceptance test. Every leaderboard row carries two independently computed scores: a signal score that is stake-independent (mean closing-line value per bet, with n and a 95% CI) and a staking score that is PnL-dependent (ROI, drawdown, units). A strategy must be able to rank top-decile on signal while flat on staking, and the board must show both columns.

Status. Design written on two trees; the board has zero rows because zero bets are graded.

Owner. desk/leaderboard.html, hub/leaderboard.html (design) ; origin/leaderboard.html (claimed)

Blocker. Nothing can be graded until R1 and R2 close. See S05.

Evidence. repo artifact - design only, board empty

R6 Track the depth of the replacement, not just the fact of a replacement NOT MET

'Starter out' and 'third-string guard starting' are different events with different expected effects. Counting only the fact treats them as identical and throws away the signal.

Acceptance test. For each absent starter: the ordinal depth of the replacement (1st, 2nd, 3rd, 4th string or undrafted/free-agent pickup), the club chart URL, and the chart's as-of date. A row without an as-of date is published as unverified, not as fact.

Status. A named replacement is joined for 41 of 76 Week 10 absences. Zero of 76 carry a chart as-of date, and no ordinal depth string is recorded anywhere.

Owner. data/desk/deficiencies.json, data/desk/depth.json

Blocker. Club charts are club-published, usually labelled unofficial, carry no date, and one club (Houston) publishes an image. See S06, S07.

Evidence. repo artifact - club charts, self-labelled unofficial

R7 Compute correlations only from officially sourced numbers and publish n with each value PARTIAL - DEFECT CONFIRMED

A correlation is the input to the parlay leg screen. An r with no n is unfalsifiable, and an r computed on unlogged data is a guess dressed as a measurement.

Acceptance test. Every published coefficient carries n, the official source URL, a 95% CI, and a plain reading. A coefficient whose CI contains 0 is labelled 'not distinguishable from no relationship' and is not used to price anything.

Status. n is published with every value, but one published coefficient does not reproduce from the data it cites, and its prose reading has the sign backwards. See V-C1 on the verification page for the recomputation.

Owner. data/desk/correlations.json

Blocker. None: this is a defect, not a data gap. Fix is in S08.

Evidence. repo artifact - recomputed this session, one value wrong

R8 Define a demotion gate that sends a live strategy back to paper NOT MET

A promotion gate with no demotion gate is a one-way door: a strategy that was lucky once stays live forever. The demotion rule is what makes the promotion rule mean anything.

Acceptance test. A written rule with numeric thresholds, a look-back window, and an automatic action: for example, return to paper when the rolling 200-bet closing-line value is negative, or when the 95% CI on ROI contains zero over the last 200 graded bets, or on any data provenance failure. Every demotion is logged with its trigger.

Status. Promotion gates G1-G8 are written. No demotion threshold exists anywhere in the repository.

Owner. data/desk/strategies.json (gates G1-G8) ; origin/data/gates.json (claimed)

Blocker. Thresholds need a decision, not a fetch. See S04.

Evidence. repo artifact - promotion gates only
